## 一、新增一个测试单元的方法

### 1.1 这套东西在做什么

每个「单元」= 一个你想搞懂的 C 函数（`compute_generic_conv1d`、`compute_generic_gru`……）。

- **C 侧**：把该函数从库里调起来，喂**受控的假设数据**，把输出按固定格式打到 stdout；
- **Py 侧**：用 PyTorch 写出数学等价实现，喂**同一份数据**，按**同一格式**打出来；
- **驱动器**：跑两边、按名字配对、逐项算误差、把超差的地方高亮。

核心是「**同一份数据 + 同一套校验规则**」。任何一侧多接受一点、少校验一点，对比结果就是假的。

### 1.2 四步

#### 第 1 步：写用例数据 `scripts/unit_cases/<unit>.json`

```json
{
  "unit": "gru",
  "tolerance": 1e-3,
  "bias": [...],
  "float_weights": [...],
  "inputs": [[...], [...], [...]]
}
```

字段约定（**两侧的校验规则必须逐字对齐**）：

| 字段 | 类型 | 合格条件 | 不合格时 |
|---|---|---|---|
| `bias` | 扁平数字数组 | 长度精确匹配 | 该字段单独退回硬编码保底 |
| `float_weights` | 扁平数字数组 | 长度精确匹配 | 同上 |
| `inputs` | 二维 `[帧][帧内元素]` | 非空、帧数 ≤ 16、每帧长度精确匹配 | 同上（整段不采纳，不是采纳半截） |
| `tolerance` | 数字，可选 | — | 取默认 `1e-3` |

#### 第 2 步：C 侧 `examples/rnn_unit.c`

宿主已按职责拆成 5 个文件（2026-09-26 拆分，**功能不变**），加单元时按类别往对应文件里塞：

| 文件 | 放什么 | 加一个单元要动它吗 |
|---|---|---|
| `rnn_unit.c` | 主流程：`arch`、各 `xxx_unit()` / `load_xxx_case()`、`main()` 分发 | ✅ 加 `xxx_unit()` 和 `main()` 里的注册 |
| `rnn_unit.h` | 宏定义（`NB_INPUTS` / `NB_OUTPUTS` / `NB_FRAMES`） | 一般不用 |
| `rnn_unit_data.h` | 保底参数（`static const` 数组） | ✅ 加该单元的保底数据 |
| `rnn_unit_util.h` | 辅助函数声明、JSON 容量宏 `UJ_*`、`UjEntry` / `UjDoc` | 一般不用 |
| `rnn_unit_util.c` | 辅助函数实现（`uj_*` JSON 读取器 / `print_item` / `auto_case_path`） | 一般不用 |

1. 把保底数据写成 `static const` 数组放进 `rnn_unit_data.h`（JSON 读不到时用）；
2. 在 `rnn_unit.c` 写一个 `load_xxx_case()`：先 `memcpy` 保底值，再用 `uj_get_floats()` / 逐帧 `uj_get("inputs[i]")` 覆盖；
3. 写一个 `xxx_unit(case_path)`，用 `print_item()` 打点；
4. 在 `main()` 里注册：`if (!strcmp(unit, "xxx")) return xxx_unit(case_path);`

> ⚠️ **只有新增 / 删除 `.c` 文件时才需要动构建。** 改的是 `Makefile.am` 的 `rnn_unit_SOURCES`（头文件另加进 `noinst_HEADERS`），然后重新生成 `Makefile.in` / `Makefile`：
> ```bash
> automake --foreign        # 依据 Makefile.am 重生成 Makefile.in
> ./config.status Makefile  # 依据 Makefile.in 重生成 Makefile
> ```
> **不要直接改 `Makefile` / `Makefile.in`** —— 它们由 configure 生成、且在 `.gitignore` 里，手改会被下次 `make` 覆盖。
> 只加或改**头文件**不必登记也能编（自动依赖跟踪 `.deps/*.Po` 会让相关 `.o` 重编），登记进 `noinst_HEADERS` 只是为了进 `make dist` 的包。

#### 第 3 步：Py 侧 `examples/rnn_unit.py`

1. 写一个 `xxx_unit(case, out=sys.stdout)`，用 `emit()` 打点；
2. 在 `UNITS` 字典注册：`"xxx": xxx_unit`。

#### 第 4 步：跑

```bash
make rnn_unit                       # 编译 C（驱动器不管这步）
uv run scripts/unit_check.py xxx    # 跑双方 + 对比 + 高亮
```

用例文件的路径**两侧程序会自己按约定去找**（C 用 `argv[0]` 的真实路径推出可执行文件所在目录，Py 用 `__file__` 推），所以下面两条也能直接读到用例数据，不必手打路径：

```bash
./rnn_unit conv1d                    # 自动找 scripts/unit_cases/conv1d.json
uv run examples/rnn_unit.py conv1d   # 同上
```

驱动器还会额外把绝对路径显式传下去，并核对「两侧读的是不是同一份数据」。

### 1.3 输出协议（两侧格式必须完全一致）

```
[<unit>.<output>#<frame>] <v0> <v1> <v2> ...
```

例：

```
[conv1d.out#0] 2.66641211e-02 -1.12817980e-01 ...
[conv1d.mem#0] 0.00000000e+00 ... 1.00000000e+00
```

C 用 `printf(" %.8e")`，Python 用 `"%.8e"`。

> **不要用 `%f`。** 它只有 6 位小数，float32 之间的真实差异（1e-7 级）会被直接抹掉，对比就失去意义了。

### 1.4 三条纪律（都是踩过的坑）

1. **两侧校验规则必须一致。** 曾出现 C 是「全有全无」保底、Python 是「逐字段」保底，导致 JSON 与编译进 C 的保底数据不同时，两边读到两份数据却报告「数值不一致」——最难查的假故障。
2. **`inputs` 要么全部合格、要么整段不采纳。** 曾出现 C 提交了出错帧之前那几帧，两侧帧数不同。
3. **C 的 `NB_FRAMES` 与 Python 的 `MAX_FRAMES` 必须相等。**

### 1.5 容差怎么定

C 的 tanh/sigmoid **不是精确函数**：`src/nnet_arch.h:79` 的 `HIGH_ACCURACY` 是注释掉的，走的是 `vec_tanh()` → `tanh_approx()`（有理分式逼近），AVX 路径还用了 `_mm256_rcp_ps` 快速倒数，相对误差约 **3.7e-4**。

- 单层（如 conv1d）：`1e-3` 够用，实测 max|Δ| ≈ 2e-5 ~ 6e-5；
- 三层 GRU（384 维、每层几百个累加项）：误差会累积，把该单元的 `tolerance` 单独放宽到 `1e-2` 更实际。

### 1.6 一个提效技巧：把中间状态也打出来

除了输出，把**纯搬运的中间量**也按协议打出来（如 conv1d 的 `mem`）。

这类项两侧应当**逐位相同**。它一旦相同，就证明「数据加载 + 状态搬运」这条链路是对的，剩下的差异只能是数学近似：

```
  conv1d.mem#0                8     0.000e+00     0.000e+00  PASS   ← 逐位相同，管线自检
  conv1d.out#0                8     2.908e-05     3.905e-04  PASS   ← 有差异，来自 tanh 近似
```

这样能把「管线接错了」和「数学近似」这两类问题分开。**建议从 `conv1d` 开始的原因就在这里**：它的 `mem` 是天然的管线自检点。

### 1.7 新单元检查清单

- [ ] `scripts/unit_cases/<unit>.json` 写好
- [ ] C 侧 `main()` 注册
- [ ] 新增了 `.c` 文件的话：已改 `Makefile.am` 的 `rnn_unit_SOURCES`，并 `automake --foreign && ./config.status Makefile`
- [ ] Py 侧 `UNITS` 注册
- [ ] 两侧字段校验规则一致
- [ ] 除了输出，还把中间状态打出来（GRU 尤其要打 `state`）
- [ ] `make rnn_unit` 后跑 `uv run scripts/unit_check.py <unit>` 全绿，**且报告里两侧的 `src` 都是 `json`**（出现 `builtin` 说明跑的是保底数据，结论不算数）

### 2.4 对比驱动器的输出怎么读

```
C      : /Users/chengmo/Work/rnnoise/rnn_unit
python : /Users/chengmo/Work/.venv/bin/python3 (examples/rnn_unit.py)

conv1d  tol=1.0e-03
  case: scripts/unit_cases/conv1d.json   src : bias=json weights=json inputs=json
  item                        n        max|Δ|     max|Δ|rel  result
  conv1d.mem#0                8     0.000e+00     0.000e+00  PASS
  conv1d.out#0                8     2.908e-05     3.905e-04  PASS
```

`case:` 是驱动器实际传给两侧的用例文件，`src:` 是两侧程序自己报的「每个字段到底来自哪里」。

| 标记 | 含义 |
|---|---|
| 绿色 `PASS` | 全部元素都在容差内 |
| 红色 `FAIL` | 有元素超容差，下方会展开逐元素表格，超阈值行标红 |
| 红色 `SIZE` | 两侧长度不同 |
| 红色「仅 C 有 / 仅 py 缺」 | 一边根本没输出这一项 |
| 黄色 `max(Δ)` | 超过容差的 10%，接近阈值，提前预警 |
| 黄色「数据来源不一致」 | 两侧读到的数据不同，**此时结论无效** |
| 红色横幅「两侧都在用内置保底数据」 | 用例文件没找到或没读进去，**这次对比不验证真实数据，结论不算数**；末尾汇总里也会单独计数 |

| 参数 | 作用 |
|---|---|
| `-t 1e-6` | 临时覆盖容差 |
| `-v` | 附带打印双方原始输出 |
| `--py <path>` | 指定解释器 |
| `FORCE_COLOR=1` | 重定向到文件时也保留颜色 |

退出码：有失败 = `1`，全绿 = `0`。
